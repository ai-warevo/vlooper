Проект **vLooper** — это модульная агентская система, предназначенная для автономного выполнения задач (в частности, автоматического исправления ошибок в GitHub-репозиториях с помощью ИИ).

В отличие от традиционных линейных конвейеров, vLooper использует **реактивную архитектуру на основе шагов**. Вместо выполнения одной монолитной задачи система разбивает работу на дискретные, отслеживаемые шаги, которые могут динамически перепланироваться на основе обратной связи в реальном времени.

## Основные уровни архитектуры

### 1. Слой обнаружения и планирования (`Scanner` & `SchedulerService`)
Этот слой отвечает за поиск работы и формирование первоначальной дорожной карты.
* **Сканирование:** `Scanner` отслеживает GitHub на предмет новых Issue или Pull Request и сохраняет их в базе данных.
* **Первичное планирование:** При обнаружении задачи `SchedulerService` немедленно генерирует последовательность атомарных шагов (например, *issue_fetcher* $\rightarrow$ *git_isolator*), необходимых для начала работы.
* **Реактивное перепланирование:** «Мозг» системы. Если шаг завершается неудачей или возвращает критическую обратную связь (например, ошибки тестов), `SchedulerService` может динамически внедрить в очередь текущей задачи исправляющие шаги (например, *test_healer*, *ai_fixer*).

### 2. Цикл выполнения и оркестрации (`VLooperDaemon`, `RoleRegistry`, `Synthesizer`)
Демон работает как непрерывный потребитель задач из базы данных.
* **Пошаговая обработка:** `VLooperDaemon` работает в бесконечном цикле, извлекая отдельные **Шаги (Steps)**, а не целые задачи. Это обеспечивает высокую отказоустойчивость: если шаг не удался, внимание требуется только к этому шагу (или его последующему исправляющему шагу).
* **Реестр ролей:** Для обеспечения слабой связности агенты не жестко запрограммированы. Вместо этого `RoleRegistry` сопоставляет идентификаторы ролей с конкретными исполнителями (например, связь "test_runner" с функцией `test_runner_agent`).
* **Синтез контекста:** `Synthesizer` готовит высокоинформативные «Миссии» (Mission Briefs) для каждого агента. Он объединяет глобальный контекст задачи, требования текущего шага и историю выполнения всех предыдущих шагов в единый набор инструкций.

### 3. Поток данных и управление шагами (`Database` & `Step Lifecycle`)
Система опирается на базу данных как на общее состояние и шину связи между агентами.
* **Атомарные шаги:** Каждое действие записывается в таблицу `tasks_steps`, которая отслеживает его статус (PENDING, RUNNING, COMPLETED, FAILED), входные данные, выходные данные и ошибки.
* **Автоматическая передача данных:** vLooper автоматически обеспечивает поток данных, принимая `output_data` завершенного шага и внедряя их в качестве `input_data` для следующего шага в последовательности.

### 4. Слой персистентности (`Database`)
База данных является единственным источником истины, управляя:
* **Состоянием задач:** Высокоуровневый статус репозиториев и Issue, над которыми ведется работа.
* **Гранулярностью шагов:** Детальный аудит каждой атомарной операции, выполненной любым агентом.
* **Миграциями:** Надежная система эволюции схемы базы данных по мере роста проекта.

## Использованные паттерны проектирования

| Паттерн | Применение в vLooper |
| :--- | :--- |
| **Producer-Consumer** | `Scanner` производит задачи $\rightarrow$ `Daemon` потребляет атомарные шаги из БД. |
| **Реактивное планирование** | Система динамически изменяет план выполнения задачи на основе результатов шагов. |
| **Registry Pattern (Реестр)** | Декупаж имен ролей от их реализации через `RoleRegistry`. |
| **Command / Step Pattern** | Инкапсуляция каждого дискретного действия в отслеживаемую запись БД. |
| **Синтез контекста** | Объединение разрозненных состояний и истории в связные инструкции для ИИ-агентов. |

## Резюме
Архитектура vLooper спроектирована так, чтобы быть **высокоотказоустойчивой**, **масштабируемой** (несколько демонов могут обрабатывать шаги одновременно) и **внутренне адаптивной** к непредсказуемому характеру процесса отладки ПО.
