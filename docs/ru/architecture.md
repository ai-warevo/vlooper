</div> 

---

Проект **vLooper** представляет собой модульную, событийно-ориентированную систему с многослойной структурой, предназначенную для автономного выполнения задач (в частности, автоматического исправления ошибок в GitHub-репозиториях с помощью ИИ).

Дизайн системы можно охарактеризовать как сочетание паттернов **«Конвейер» (Pipeline)**, **«Луковичная архитектура» (Middleware/Onion)** и **«Наблюдатель» (Event Bus)**.

## Основные уровни архитектуры

### 1. Уровень оркестрации (`VLooperDaemon`)
Это центр управления системой. Демон работает в бесконечном цикле, выполняя следующие функции:
* **Сканирование:** Использует `Scanner` для поиска новых задач в базе данных или через внешние API.
* **Управление жизненным циклом:** Извлекает задачи, помечает их как «в работе» (claim) и инициирует выполнение.
* **Изоляция:** Гарантирует работу только одной копии демона с помощью файловой блокировки (`fcntl.flock`).

### 2. Движок исполнения (`TaskPipeline` & Middleware)
Вместо жестко прописанной логики, vLooper использует гибкий конвейер обработки задач:
* **Middleware (Слои «луковицы»):** Обертки вокруг основного процесса. Они отвечают за сквозную функциональность (cross-cutting concerns), такую как глобальная обработка ошибок (`GlobalExceptionHandlerMiddleware`), проверка авторизации и ограничение попыток повтора (`RetryLimitMiddleware`).
* **Steps (Шаги):** Последовательные атомарные операции, выполняемые внутри защищенного контекста:
    1. Подготовка окружения (`git_isolate_repository`).
    2. Запуск тестов прогона («harness») (`run_repository_tests`).
    3. Применение ИИ-исправления (`apply_ai_fix`).
    4. Создание Pull Request (`github_create_pull_request`).

### 3. Событийный уровень (`EventBus` & Handlers)
Для обеспечения слабой связности (loose coupling) используется шина событий. Это позволяет отделить основную логику выполнения от побочных эффектов:
* **События:** Когда происходит что-то важное (задача взята в работу, тест пройден, PR создан), генерируется событие (например, `EventName.TASK_FINISHED`).
* **Обработчики (Handlers):** Подписанные на шину компоненты реагируют на эти события. Например, `GitHubNotificationHandler` отправит уведомление, а `TaskStatusHandler` обновит статус в базе данных. Это позволяет добавлять новые реакции на действия системы, не меняя код самого конвейера.

### 4. Слой сервисов и клиентов (`services/` & `clients/`)
Соблюдается четкое разделение ответственности:
* **Clients:** Низкоуровневые инструменты для прямого взаимодействия с внешними API (Git, GitHub, OpenCode).
* **Services:** Высокоуровневая бизнес-логика, которая оркестрирует работу клиентов (например, `ai_service` управляет взаимодействием с языковой моделью).

### 5. Слой персистентности (`persistence/`)
Используется для хранения состояния задач и истории их выполнения. Присутствует система миграций базы данных, что обеспечивает эволюцию схемы данных без потери информации.

## Использованные паттерны проектирования

| Паттерн | Применение в vLooper |
| :--- | :--- |
| **Daemon** | Фоновый процесс, постоянно мониторящий внешние источники задач. |
| **Pipeline / Interceptor** | Последовательная обработка задачи через цепочку шагов и middleware. |
| **Observer (Event Bus)** | Декоппинг логики выполнения от систем уведомлений и обновления БД. |
| **Layered Architecture** | Четкое разделение: UI $\rightarrow$ Daemon $\rightarrow$ Services $\rightarrow$ Clients $\rightarrow$ Infra/DB. |
| **Strategy / Step** | Инкапсуляция каждой стадии работы (тесты, фикс, PR) в отдельный вызываемый объект. |

## Резюме
Архитектура спроектирована так, чтобы быть **высокорасширяемой** (легко добавить новый шаг или обработчик события) и **отказоустойчивой** (благодаря middleware-слоям обработки ошибок и механизмам повторов). Система хорошо подходит для сложных, долгоживущих автоматизированных процессов.
